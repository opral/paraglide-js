# Private 3x-ui per-locale build experiment

This experiment uses the actual Vite `experimentalPerLocaleBuild: true` compiler plugin and `createBuilder().buildApp()`, compiling all 13 full catalogs and all three HTML entries. It compares Spanish `/login` with optimized native i18next's early selected-locale preload. This is a private feasibility result, below the 10% gate; no product source change or performance claim qualifies.

Pinned app: MHSanaei/3x-ui `74c3cc38821cabd66ad316ea562851422d0b0063`. Actual builder: Node26.3.1, Vite8.3.4, Rolldown1.2.12, captured separately in `build-provenance.json`. Compiler output comes from the frozen `/root/repos-iii/paraglide-client-split-current-api/dist`; implementation leaf hashes are recorded there. The compiler's locale manifest incorrectly records its own dependency versions Vite8.1.4/Rolldown1.1.5. This provenance bug does not substitute the actual app builder.

## Result and limits

Static selected login graph BrotliQ4: 756,723→683,958 bytes (9.62% reduction). Whole browser resource encoded bytes: 755,866→683,586 (9.56%), 21→18 resources. One exploratory pair per profile showed FCP/LCP 1,020→976 ms on desktop (4.31%) and 4,496→4,140 ms with the mobile viewport (7.92%). These single pairs do not establish an improvement. Corrected probes are captured separately: desktop FCP/LCP 1,100→1,060 ms (3.64%), readiness before hash collection 1,283→1,240 ms (3.35%); mobile FCP/LCP 4,636→4,336 ms (6.47%), readiness 5,041→4,744 ms (5.89%). All controls show identical Spanish greeting/input placeholders and zero browser errors. Still below 10%; no repeated timing batch or exhaustive catalog parity qualification was run. Shared-host unrelated processes may contribute noise. Historical `translatedReadyMs` in `desktop-pair.json` and `mobile-pair.json` was sampled after awaiting response body hashes, and must not be interpreted as first-visible readiness. Their metadata is corrected without altering samples. `startup-probe.mjs` now captures readiness before collecting hashes. Mobile uses a 390×844 viewport, 150ms RTT, 1.6Mbps down, 0.75Mbps up, 4× CPU; desktop 1365×768, 80ms, 20Mbps down, 2Mbps up, 3× CPU. Both are HTTP/1.1 loopback without TLS/H2. Service workers are blocked equally; this app's identical public worker has an empty fetch handler.

Full catalog input: 2,589 IDs per locale,13 locales,123 input messages and no markup. Dynamic compatibility calls retain the complete namespace; no manual catalog pruning. Native locale selection reloads the document, matching fixed-locale output. Generated options.locale mismatch warning remains; Spanish compat chunk is777,138 raw bytes/71,555 BrotliQ4. No assertion that dispatchers become literals. Existing conversion normalizes718 CRLF strings toLF across40,053 comparisons; exact-string parity is not established. Broader rich formatting/locale switch and full application route parity have not been qualified.

The manifest/static graph audit verifies all13 outputs contain3 entries and same-relative-name assets have identical content:0 collisions across1,303 unique shared assets. Fixture hosting selects HTML by exact supported `lang` cookie (subpage also `subLang`) and serves original root asset URLs from the verified shared asset pool. It does not implement all native browser-language/alias fallback behavior. HTML varies byCookie. Identical public files were verified against native; no worker compilation variant exists. Never mutate a served output directory, because compressed responses are cached.
